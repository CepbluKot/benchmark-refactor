# Пространства, бенчмарки и шаблоны стратегий

## Цель

Демо-интерфейс показывает будущую работу с бенчмарками как с самостоятельными
заданиями. Пользователь выбирает пространство, создаёт в нём бенчмарк для одной
таблицы ClickHouse, настраивает его из готового шаблона стратегии и смотрит
запуски в контексте этого пространства.

## Границы

- Пространство агрегирует только бенчмарки и их запуски.
- Источники данных общие: их список, учётные данные и доступность не зависят от
  пространства.
- Один бенчмарк соответствует ровно одной исходной таблице.
- Это локальная демо-модель интерфейса. `workspace_id`, название бенчмарка и
  шаблон стратегии не добавляются в экспортируемый `BenchmarkConfig`.
- Реальный запуск, каталог ClickHouse и проверка соединения не появляются в
  этом изменении.

## Навигация

В постоянном боковом меню остаются:

1. **Бенчмарки** — список бенчмарков выбранного пространства и создание нового.
2. **Запуски** — история запусков бенчмарков выбранного пространства.
3. **Источники данных** — общие подключения ClickHouse.
4. **Стратегии поиска** — служебный каталог шаблонов.

Вкладка **Банки правил** удаляется. Её место занимает настройка правил внутри
бенчмарка и шаблонов стратегий.

В верхней панели перед заголовком размещается селектор пространства. Он
показывает текущее пространство, переключает между существующими и содержит
действие «Создать пространство». Создание требует только название; технический
идентификатор создаётся интерфейсом и не показывается пользователю.

## Модель состояния демо

```text
Workspace
  id: generated local identifier
  name: user-visible name

BenchmarkTask
  workspaceId: Workspace.id
  name: user-visible name
  templateId: StrategyTemplate.id
  config: BenchmarkConfig

StrategyTemplate
  id: stable local identifier
  name: user-visible name
  strategy: BenchmarkStrategy
  config seed: rules, queries, limits, scoring
  description: user-facing explanation
```

`DataSource` остаётся без `workspaceId`. `DemoRun` получает `workspaceId` через
бенчмарк при создании и показывается только в соответствующем пространстве.

Перед созданием бенчмарка выбранный шаблон копируется. Дальнейшие изменения
правил, запросов, лимитов и scoring меняют только `BenchmarkConfig` конкретного
бенчмарка. Редактирование шаблона не меняет уже созданные бенчмарки.

## Страница «Бенчмарки»

Таблица показывает только текущий workspace:

- название бенчмарка;
- `database.table`;
- источник данных;
- понятное название стратегии;
- состояние настройки;
- последний запуск;
- действия «Настроить» и «Запустить демо».

Кнопка «Создать бенчмарк» открывает отдельный экран. В нём пользователь проходит пять разделов настройки и выбирает одну исходную таблицу в формате `база.таблица`.

## Создание и настройка бенчмарка

Экран состоит из пяти последовательных разделов.

### 1. Основное

- название бенчмарка;
- выбранное пространство, только для информации и смены при необходимости;
- шаблон стратегии поиска.

Технический ID не вводится пользователем. Для совместимости с текущим движком
интерфейс производно формирует `BenchmarkConfig.id` из имени и локального
идентификатора.

### 2. Источник и таблица

- источник данных ClickHouse;
- исходная база;
- исходная таблица;
- тестовая база (`test_database`) для таблиц-кандидатов.

База и таблица вводятся вручную. Сохранение создаёт `tables` как единственную
пару `database.table`; пользователь не может выбрать `*`, список таблиц или
несколько баз из этого потока.

### 3. Стратегия поиска

В интерфейсе используются понятные названия, техническое значение сохраняется
в `BenchmarkConfig.strategy`:

| Название | Техническая стратегия | Состав поиска |
| --- | --- | --- |
| Поэтапный подбор структуры | `sequential_phased_topn_strategy` | Типы, кодеки, `ORDER BY`, skip-индексы, финальная проверка |
| Подбор типов колонок | `types_strategy` | Типы и кодеки |
| Подбор skip-индексов | `indexes_strategy` | Индексы и гранулярность |
| Подбор порядка сортировки | `sequential_topn_strategy` | Кандидаты `ORDER BY` и отбор Top-N |

### 4. Правила вариантов

- `column_rules` и `codec_rules`;
- `index_rules`, варианты индекса и его `granularity`;
- `order_by_rules` и кандидаты `ORDER BY`;
- `column_order`;
- `index_granularity_values`.

Эти поля записываются в `global_rules` и связанные поля `BenchmarkConfig`.
Пользователь не работает с отдельным rule bank на странице бенчмарка.

### 5. Нагрузка и оценка

- `queries` и ручные SQL-запросы;
- лимиты поиска и измерений;
- `scoring` и ограничения Top-N.

## Страница «Стратегии поиска»

Это служебный каталог редактируемых базовых шаблонов. Карточка шаблона содержит:

- название и описание;
- понятный тип стратегии;
- состав фаз;
- число правил типов/кодеков, индексных правил и запросов;
- число использующих бенчмарков;
- действия «Создать бенчмарк на основе», «Изменить» и «Дублировать».

Редактор шаблона использует те же пять разделов, что и бенчмарк, кроме источника
и таблицы. Он хранит только переносимые начальные правила, запросы, лимиты и
scoring. Тестовая база и источник определяются в конкретном бенчмарке.

## Запуски

Список и детали запусков фильтруются по текущему пространству. Снимок запуска
продолжает хранить `BenchmarkConfig`, поэтому последующие изменения бенчмарка
не переписывают историю.

## Ошибки и пустые состояния

- При создании требуются название, источник, исходная база, таблица и тестовая
  база.
- Нельзя создать бенчмарк в отсутствующем пространстве.
- При отсутствии бенчмарков показывается ADQM empty state с действием создания.
- Удаление пространства не удаляет общие источники. В демо удаление запрещено,
  пока в пространстве есть бенчмарки.

## Визуальные правила

Все кнопки, поля, селекты, вкладки, таблицы, карточки, empty state и диалоги
используют `@adqm/gpb-ui`. Пространство выбирается в верхнем селекторе; для
списков, форм и карточек применяются поставляемые компоненты и локальные
шрифты библиотеки. Новая страница не вводит отдельный UI-kit или внешние assets.

## Проверка реализации

- TypeScript typecheck;
- проверка создания, переключения и ограниченного удаления пространств;
- проверка, что источники не меняются при смене пространства;
- проверка, что созданный бенчмарк содержит одну `database.table`;
- проверка независимости копии бенчмарка от шаблона;
- существующие demo checks, round-trip `BenchmarkConfig`, production build и
  `git diff --check`.
