Что мы делаем
Делаем движок бенчмарка DDL, который автоматически перебирает варианты схемы таблиц, запускает на них набор SQL-запросов, сохраняет результаты и помогает выбрать лучший вариант на основе score. Сейчас practical-first ориентир — ClickHouse, но архитектура уже разложена на интерфейсы и расширяемые стратегии.

Текущая архитектура решения

Конфиг и валидация: models.py
Здесь описан весь контракт JSON-конфига: подключения, benchmark’и, rule banks, режимы перебора, запросы, лимиты, table-level override.
Важные поля:

mode (types/indexes/sequential/combined)
max_iterations, sequential_top_n
insert_rows_limit (общий fallback)
insert_rows_limits (лимиты по mode/stage, включая будущие custom mode-ключи)
Загрузка и сборка конфига: loader.py
Конфиги собираются либо из project-файла и ссылок на секции, либо из отдельных JSON-секций (например из base64 env).
Loader проверяет ссылочную целостность: валидные connection_id, rule_bank, default_rule_banks.

Резолвинг правил: resolver.py
Делает merge global + table rules и превращает config-правила в runtime-правила.
Поддержаны режимы источника правил:

global_bank_only
global_bank_with_inline_priority
inline_only
DDL и правила мутаций:

clickhouse_ddl.py — парсер/рендерер DDL в объектную модель TableDDL
column_rules.py + column_variants.py — варианты типов/кодеков
index_rules.py + index_variants.py — варианты индексов
Матчинг by_type строгий по полной строке типа.
Комбинатор вариантов (расширяемый): combiner.py
Вынесен интерфейс VariantGenerationStrategy и реестр MODE_VARIANT_STRATEGIES.
Встроенные стратегии: types, indexes, sequential, combined.
Можно регистрировать новые режимы без правки if/elif в ядре.

Планирование и исполнение: benchmark_engine.py
Главные сущности:

BenchmarkPlanner — из конфига делает table-level планы TableBenchmarkPlan
BenchmarkEngine — из TableBenchmarkPlan строит VariantJob
BenchmarkRunner — запускает jobs через адаптер выполнения и пишет результаты в store
Ключевые интерфейсы:
MetadataProvider (откуда брать метаданные и DDL)
BenchmarkExecutionAdapter (как реально выполнять бенчмарк)
BenchmarkResultStore (куда сохранять результаты)
BenchmarkRunIdProvider (как выдавать serial run id)
TableExecutionStrategy (как исполнять table plan по mode)
Запросы и naming:

query_generator.py — auto-генерация тестовых SQL
naming.py — имена variant-таблиц
Работа с БД: fetcher.py
Сейчас это ClickHouse-специфичный fetcher (DDL, списки таблиц, insert/select, метрики).

Как идет поток выполнения (end-to-end)

Конфиг валидируется и собирается в BenchmarkRootConfig.
BenchmarkPlanner раскрывает selectors БД/таблиц, применяет override, резолвит правила, формирует TableBenchmarkPlan.
BenchmarkEngine читает исходный DDL, строит query plan, генерирует варианты через combiner, создает VariantJob.
BenchmarkRunner выбирает стратегию исполнения:
default стратегия: обычный прогон всех jobs
sequential стратегия: stage1 types -> выбор top-N по score -> stage2 indexes только на лучших DDL
Каждый job уходит в execution_adapter.execute_variant(job).
Результат сразу пишется в result_store; в памяти полный массив результатов не копится.
На запуск выдается единый benchmark_run_id (serial), общий для всех benchmark’ов в этом run.
Как сейчас устроены лимиты вставки строк

Есть insert_rows_limit — общий fallback.
Есть insert_rows_limits — по режимам/stage (types/indexes/combined/sequential) и будущим custom mode-ключам.
Приоритет вычисления лимита для конкретного job:
insert_rows_limits[variant_meta.mode]
затем insert_rows_limits[job.mode]
затем fallback insert_rows_limit
Итоговый лимит приходит в VariantJob.insert_rows_limit, и адаптер выполнения использует его для INSERT ... SELECT ... LIMIT N.
