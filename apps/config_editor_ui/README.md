# Редактор конфигураций DDL Benchmark Engine

Веб-интерфейс для настройки экспериментов по подбору физической структуры таблиц
ClickHouse. Работает с файлом бенчмарков действующего движка — тем же форматом,
который описан в [`src/models.py`](../../src/models.py).

Это **только редактор файла конфигурации**. Он не запускает бенчмарк, не читает
каталог таблиц, не проверяет подключение и не применяет DDL к исходной таблице.

## Что уже есть

- импорт файла бенчмарков (`benchmarks.*.json`) и project-конфига с inline-списком
  `benchmarks`;
- редактирование всех полей `BenchmarkConfig`, включая `global_rules`,
  `queries`, `scoring`, лимиты и `table_rules`;
- локальная проверка структуры и ограничений модели;
- просмотр JSON выбранного бенчмарка или всего файла;
- экспорт JSON с сохранением исходной структуры файла.

## Чего нет и почему

| Возможность | Что нужно |
|---|---|
| Запуск и мониторинг | HTTP API поверх текущего движка. `apps/m0_control_plane` — отдельный M0-прототип на Hatchet, это не API запуска ClickHouse-бенчмарка |
| Каталог баз, таблиц и колонок | обращение к ClickHouse через сервер |
| Проверка подключения | то же |
| Проверка формулы средствами движка | серверный вызов `src/scoring_validation.py` |
| Экраны результатов | API результатов |

Имена баз и таблиц вводятся вручную: без серверного каталога проверить их
существование нельзя, а выдумывать список недопустимо.

## Уровни проверки

1. **Синтаксис JSON** — выполняется здесь.
2. **Структура и локальные ограничения** — выполняется здесь, зеркалит pydantic-модель.
3. **Межфайловые ссылки** (`connection_id`, `rules.rule_bank`) — выполняется здесь,
   если через «Справочные файлы» загружен `connections.*.json` и/или `rule_banks.*.json`.
   Пароли из файла подключений не читаются и не отображаются.
4. **Проверка движком** — недоступна без сервера. Формула scoring проверяется здесь
   только локально (имена, функции, запрещённые конструкции); такие сообщения
   помечены как «локальная проверка».
5. **Подключение и объекты БД** — недоступна без сервера.

Проверка структуры не гарантирует корректность SQL и доступность таблицы.

## Сохранность файла

- поля, которых не было в исходном файле, не дописываются значениями по умолчанию;
- отсутствие поля, пустой список и явное значение различаются;
- незнакомые ключи и значения с неподдерживаемым типом сохраняются и показываются
  как ошибки, а не удаляются молча;
- форма записи `granularity` массивом сохраняется как массив.

Проверка «импорт → экспорт без потерь» на реальных конфигурациях проекта:

```bash
npm run check:roundtrip -- ../../configs/hits_postgres/benchmarks.hits_postgres.sequential_topn.local.json
```

## Разработка

```bash
npm install
npm run dev
```

Проверки:

```bash
npm run typecheck
npm run build
```

## Развёртывание

```bash
docker build -t ddl-benchmark-config-editor .
docker run --rm -p 8080:8080 ddl-benchmark-config-editor
```

Адрес будущего внутреннего API задаётся в `runtime-config.js` рядом с `index.html`
и правится без пересборки образа:

```js
window.__DDL_BENCH_CONFIG__ = { apiBaseUrl: 'https://benchmark-api.internal' };
```

Контур: внешние CDN, шрифты, аналитика и телеметрия не используются; шрифты
системные. Стадия `docker build` требует доступа к npm-реестру — собирайте образ
там, где реестр доступен, либо используйте внутреннее зеркало.

Аутентификации, аккаунтов и ролей в приложении нет: доступ ограничивается контуром.

## Границы форматов

В проекте отдельно существуют конфигурации подключений, банков правил, бенчмарков
и project-обёртки. Редактор их не объединяет: файлы подключений и банков правил
загружаются только как справочники для проверки ссылок.

Текущий формат `BenchmarkConfig` не смешивается с будущим `StudyManifest`
(см. `docs/TARGET_ARCHITECTURE_REFACTOR.md`). В частности `on_error_score`
существует в текущем формате и сохраняется при редактировании.
